# ADR-002: 安全与治理采用“前期轻量、后期可升级”的分阶段模型

## 状态
Accepted

## 日期
2026-02-24

## 背景
当前用户规模有限，业务目标是先把内置 Agent 能力和通用接入逻辑做稳定。团队明确前期不追求高强度安全审查，但不能牺牲后续升级空间。

## 决策
采用三阶段安全治理策略：

### 阶段 1（当前，MVP）
1. 认证：平台用户会话 + Agent API Key（由 Registry 发放与轮换）。
2. 授权：基于角色的粗粒度权限（只读/执行/管理）。
3. 审计：记录调用最小闭环（谁在何时调用了哪个 Agent、结果状态、耗时）。
4. 隔离：项目级逻辑隔离，不做严格多租户硬隔离。

### 阶段 2（生态扩张）
1. 增加 OIDC/OAuth2 客户端凭证模式，支持第三方系统安全接入。
2. 增加细粒度策略（按资源类型/操作类型授权）。
3. 增加配额与速率限制策略中心。
4. 增加敏感操作确认流（如 DNS 变更、生产发布触发）。

### 阶段 3（规模化/企业化）
1. 支持组织级多租户隔离与专属密钥域。
2. 引入签名请求与可选 mTLS。
3. 完整审计链路（可导出、可检索、可合规留存）。
4. 对接企业 IAM 与审批系统。

## 理由
1. 与当前业务阶段匹配，避免过早复杂化。
2. 保证“先可用再增强”，但通过分层设计避免未来推倒重来。
3. 为第三方 Agent 生态留出明确升级路径。

## 影响
1. 开发：首期实现成本可控，但必须保留扩展点（认证插件、策略接口、审计事件模型）。
2. 测试：除功能测试外，需要最小安全回归（越权访问、无效 key、重放请求）。
3. 产品：前期可以更快验证价值，后续按用户规模与商业需求增强治理。

## 明确不做
1. 阶段 1 不做复杂计费结算。
2. 阶段 1 不做全量 SOC2/等保级控制项落地。
3. 阶段 1 不做重运营化 Store 审核流程。
